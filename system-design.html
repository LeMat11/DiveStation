白板开场

“我先把安全目标和更新频率定下来，然后画正常数据流；接着补控制权、超时和降级路径，最后给测试计划。这里我假设操作者链路不是安全认证链路，物理急停独立于普通网络命令。”

一份完整答案的六个评分面

每次练习结束用它自评，而不是看框图是否漂亮

1. 需求与量纲

有没有明确 Hz、ms、m、°、N、温度和允许失败行为？“实时”必须变成 deadline。

2. 边界与所有权

控制器、驱动、感知、UI 谁拥有状态？消息是命令、事件还是遥测？

3. 正常路径

从输入到执行器或从采样到结果，是否能沿箭头解释每一个转换和频率？

4. 失效与安全

掉线、卡住、过温、传感器冻结、乱序、越界时，系统停在哪里，怎样恢复？

5. 可观测性

是否记录单调时间、sequence、age、状态转换原因、队列深度和配置版本？

6. 验证与演进

如何从纯软件测试推进到 HIL 和真机？哪些接口为未来 ROS 2 或新硬件保留？

CORE 01MantaBot端到端架构

设计一套 Steam Deck 遥操作水下机器人的完整系统

15–20 分钟

机器人有双 AK45-10 电机、双舵机、IMU、深度传感器和双目相机；需要手柄控制、实时反馈、视频、急停、记录与回放。请画出 Deck 到 Raspberry Pi 5 再到硬件的架构，并说明频率、协议与掉线行为。

必须主动问

有线还是无线？最大距离？允许延迟？失联后保持、回零还是上浮？物理 E-Stop 在哪里？

必须画出

命令链、遥测链、视频链和安全链四条路径，不能把所有数据塞进一个“network”方框。

展开参考架构与追问

需求预算

Deck 输入与 UDP 命令 50 Hz；Pi supervisory control 50 Hz；双翼轨迹 200 Hz；IMU 100 Hz；深度 10 Hz；双相机目标 15 fps；WebSocket 遥测 10 Hz。控制链优先稳定低延迟，视频允许降级和丢帧。

组件与边界

  • Deck：evdev/gamepad → input mapper → 带 sequence、monotonic timestamp、source 的绝对命令包。
  • Pi 网络接收：只做验证和写入 command mailbox，不直接碰硬件。
  • 50 Hz controller：控制权仲裁、armed/E-Stop、mixer、限幅和 setpoint 生成。
  • 200 Hz motor loop：相位累加、左右镜像、MIT-mode CAN 编解码和机械限位。
  • 独立 sensor/camera workers 写入带时间戳的 SharedState；遥测层读取一致快照。

通信选择

控制命令用 UDP，理由是新包比旧包重要，配 sequence、timestamp 和 500 ms watchdog；遥测用 WebSocket 方便浏览器/GUI；视频使用 latest-frame MJPEG 或低延迟 H.264，慢客户端不应积压历史帧。

失效路径

UDP 超时清零输入并安全回零；所有 Web client 消失后控制源回到 none；相机失败不影响控制；CAN/传感器故障标记 invalid 并限制模式；物理 E-Stop 最高优先级。恢复时不得沿用旧命令，必须重新建立 source 和 armed 状态。

验证

先回放命令测试状态机，再用虚拟 CAN/无负载执行器验证限幅；故障注入丢包、乱序、冻结相机、拔传感器、过温和进程退出；最后在固定夹具、浅水、目标 3 m 水深逐级验收。

面试官可能追问

为什么不全部用 TCP？SharedState 怎样避免锁住控制循环？视频编码使 Pi 过热时怎样降级？

CORE 02MantaBot状态机 / 安全

多个命令源怎样安全地争夺同一组执行器？

15 分钟

手柄、Web 控制、巡航锁定、demo 和 E-Stop 都可能产生电机/舵机命令。设计控制权仲裁，要求临时人工接管后可以平滑返回，掉线不保留陈旧指令。

展开状态机与安全不变量

先定义不变量

  • E-Stop 永远覆盖普通命令；disarmed 时电机不能产生运动。
  • 同一时刻只有一个 actuator command owner。
  • source 切换先清空旧命令，再接受新 source 的新鲜数据。
  • 任何自动恢复都不能绕过显式 re-arm。

状态与事件

顶层可用 DISARMED、MANUAL、CRUISE_LOCKED、OVERRIDE、RAMP_DOWN、ESTOP；事件包括 ARM、LOCK、STICK_OVERRIDE、RELEASE、LINK_TIMEOUT、DISARM、ESTOP、RESET。E-Stop 作为全局转换优先处理。

平滑接管

锁定时保存 command snapshot；摇杆超过带 hysteresis 的阈值进入 OVERRIDE；释放后用 300 ms ramp 从最后人工命令回到 snapshot，避免 setpoint 跳变。解除巡航用更长 ramp 到安全中位。

实现边界

状态转换逻辑和执行器输出分开；entry/exit action 可测试；最终命令经过统一 mechanical clamp、slew-rate 和 armed/E-Stop gate，不能让每个模式各自实现一套安全逻辑。

测试矩阵

枚举 state × event；属性测试“ESTOP 后输出恒安全”；在 ramp 中途触发 E-Stop、掉线、重新连接和 source 切换；记录每次转换的 from/to/event/reason。

CORE 03MantaBot多速率实时系统

200 Hz 电机环、50 Hz 控制和 15 fps 相机怎样共存？

15 分钟

设计 Raspberry Pi 5 上的调度与数据交换，使慢相机、Web 客户端或磁盘记录不会拖慢执行器循环。说明 deadline、数据新鲜度与过载降级。

展开任务划分与过载策略

任务划分

电机轨迹 loop 200 Hz（5 ms 周期）和 supervisor 50 Hz（20 ms）独立；CAN receive、IMU、深度、相机、Web、记录分别为独立 worker。每个任务只做本频率需要的工作。

数据交换

command mailbox / immutable snapshot 带 timestamp、sequence、valid；控制线程不等待相机、网络或磁盘。相机用 size 1 的 latest-frame queue；记录用有界队列，满时按策略丢低价值数据并上报 drop count。

调度与时间

使用 monotonic clock 和 deadline-based sleep，测量实际 dt、execution time、jitter、deadline miss。不要只写 sleep(0.005) 并假设一定 200 Hz。控制热路径避免同步日志、大分配和阻塞 I/O。

降级顺序

CPU/温度上升时先降相机编码与 Web 遥测，再暂停感知，最后才限制执行器频率或进入 E-Stop；降级要有 hysteresis，避免阈值附近反复切换。

容量验证

压力测试多客户端、最大视频分辨率、记录开启与网络抖动；检查 200 Hz loop 的 P99 和最坏 overrun，而不只看平均 CPU。

CORE 04MantaBot感知 / 网络

设计双目视频、深度显示和遥测的数据管线

15 分钟

双 IMX219 输出 2 × 1280×720，Deck 端做校正和 StereoSGBM；需要原视频、深度查询、0.20 m 接近警告、记录与回放。怎样设计格式、队列、时间戳和质量监控？

展开感知管线与质量边界

主路径

Pi 采集左右图并形成带 frame_id、capture timestamp、尺寸和健康状态的 pair；只保留最新 pair，按需编码并传到 Deck。Deck 加载与当前分辨率匹配的 calibration，rectify → StereoSGBM fixed-point disparity → validity mask → Q reprojection → ROI 统计与 UI。

为什么 latest-frame

操作者更需要最新画面而不是完整历史。队列积压会让画面“流畅但延迟越来越大”，比偶尔掉帧危险。记录支路可以有独立有界队列和明确 drop policy。

安全与置信

接近警告至少要求中心 ROI 有 64 个有效像素；0.20 m 触发、0.25 m 解除形成 hysteresis。它只是操作者辅助，不作为自主避障安全认证输入。

必须监控

capture/encode/decode fps、frame age、drop count、pair mismatch、disparity valid ratio、温度和 client lag。标定 RMS 0.246 px 与 0.146 px epipolar error 不等于 metric depth accuracy，另需已知距离靶验证。

降级

先降低 fps/分辨率/编码工作量，再关闭深度计算保留原视频；如果 pair 不同步或 calibration 不匹配，标记 depth invalid，绝不显示看似合理的旧距离。

CORE 05VCA嵌入式分布式控制

为什么 500 Hz PID 必须留在 Driver，而不是放在浏览器或 Commander？

15 分钟

系统由浏览器、Commander ESP32-C6、ESP-NOW 和 Driver ESP32-C6 组成。设计静态位置、手动 PWM、流式轨迹、遥测和失联安全，并说明控制环放置位置。

展开双 MCU 架构与消息协议

控制环位置

AS5600L 读取、20 kHz PWM 和 500 Hz PID 都在 Driver 本地，避免浏览器、串口与 ESP-NOW 的非确定延迟进入反馈环。Commander 只负责 host gateway、命令转发、ACK 匹配和状态汇总。

消息分类

区分 mode/setpoint/gain/stop/config 命令与 telemetry/status/ack；每包带 version、message_id、source、timestamp/age 和 checksum 或长度验证。STOP 有独立高优先级队列，不能排在普通 trajectory 后面。

模式语义

MANUAL 直接命令有限幅 PWM；STATIC_PID 保持角度；TRACKING 接受 20 Hz 高层 setpoint，但 Driver 仍以 500 Hz 插值/执行反馈；模式切换清积分并做 bumpless transfer。

安全链

输出低电平初始化；I²C encoder fault 立即 coast 并锁存；机械 ±45° 限位只禁止向外命令，允许向内恢复；浏览器、串口、无线分别有 watchdog；恢复通信后仍需显式 re-arm。

验证

消息丢失/重复/乱序、队列塞满、Commander 重启、Driver 独立运行、encoder 拔出、limit boundary 和 mode mid-transition 全部做故障注入。

CORE 06VCA自动实验 / 安全

设计一个不会把硬件调坏的 PID 自动调参系统

15–20 分钟

Python 工具要自动执行 0→+10→−10→0° 序列，搜索 Kp、Ki、Kd 和 deadband。怎样组织 preflight、评分、实验状态、异常中止和结果复现？

展开安全自动化框架

Preflight

确认 encoder 方向、输出方向、零点、噪声、通信 age、温度、机械限位和 STOP 路径；用低幅值 polarity test，任何符号异常都不进入自动搜索。

候选生命周期

ARM → apply gains → warmup → repeated step sequence → coast → cool/check → score → persist。每一步有 deadline 和可中断点；STOP 直接进入 coast，不等当前试验结束。

评分

组合 ITAE、overshoot、settling time、steady-state error、limit-cycle amplitude 和 saturation penalty；所有分量归一化并保存原始指标，避免单个 composite score 隐藏危险行为。

Abort 条件

角度越界、持续饱和、温度上限、encoder fault、通信超时、振荡幅值或速度超过阈值立即中止并锁存原因。失败候选也保存数据，但不能作为下一轮 seed。

复现

保存固件 commit、配置、candidate ID、顺序、原始 50 Hz telemetry、环境/温度和 score 版本。已记录的 36 个候选、72 次序列和 38.5% cost reduction 应明确是该评分定义下的结果。

CORE 07Flow Sensing同步 / DAQ

设计五路压力传感器与 PIV 的硬件同步采集系统

15–20 分钟

五个 MS5803 地址相同，经 TCA9548A 接到 Teensy；压力 80 Hz，PIV 需要外部 TTL。要求数据可配对、可诊断 jitter 和 missed sample，并处理各通道零偏。

展开同步与采集架构

硬件拓扑

Teensy 通过 TCA9548A channel selection 驱动五个同地址 MS5803；400 kHz I²C。先跨五个通道启动压力转换，再读取结果，减少完全串行 conversion+read 带来的 channel skew。

共同时间基

同一个 Teensy microsecond clock 产生 1 ms、3.3 V TTL 上升沿并调度压力采样；TTL edge 定义双方 t=0。第一压力样本在已知 12.5 ms 后产生，之后固定 12.5 ms 间隔。不要用键盘开始时间或 USB 接收时间做对齐。

数据契约

每行包含 run_id、sequence、channel、raw/calibrated pressure、Teensy timestamp、TTL-relative time、scheduled time、jitter、missed count 和 sensor status；host epoch 映射只是跨设备日志辅助，不替代电气 TTL。

校准

每通道先做 zero-flow baseline，计算 Δpᵢ(t)=pᵢ(t)−mean baselineᵢ；若关注差压，可再做 reference/common-mode subtraction，但必须保留原始值和方法版本。

验证

示波器同时看 TTL 和采样标志；测 channel skew、周期 jitter、长时间漂移和 missed sample；拔掉单个传感器时其他通道仍应记录并标记局部故障。

CORE 08跨项目 Debug可观测性

机器人重连后突然运动：怎样设计系统让问题既不发生又能查清？

15 分钟

操作者 Wi‑Fi 短暂中断，界面显示已恢复，但执行器突然执行了断线前命令。请从协议、队列、状态机、日志和测试五个层面给设计与排查方案。

展开根因树与防复发设计

可能根因

  • 可靠队列在重连后补发旧增量命令；或 consumer 积压后继续消费。
  • 只检查 connection alive，没有检查 command timestamp/sequence。
  • source 切换未清 mailbox；cruise snapshot 或积分器仍保留。
  • 发送端重启导致 sequence 归零，接收端错误接受。
  • UI 显示的是 socket 状态，不是 actuator authority/armed 状态。

预防

命令用绝对 setpoint + session_id + monotonic age + sequence；有界 latest-command mailbox；超时立即 revoke authority、清命令并进入安全态；重连只建立通信，不自动恢复 armed；新 session 需要 handshake 和显式 re-arm。

排查顺序

先用执行器日志确定实际 command_id/source/session，再向上追接收、网络和发送；不要从 UI 猜。比较 capture time、receive time、apply time 和 state transition reason。

日志

统一记录 session_id、seq、command timestamp、receive/apply age、queue depth、drop count、owner、armed、state from/to/reason，以及最终限幅后的 actuator command。

测试

在每个状态下注入断网 100 ms/1 s/5 s、乱序、重复、发送端/接收端单独重启、队列满和时钟异常；不变量是“没有新 session 的显式 arm，输出不得恢复”。

OPTIONAL 09CLD实验系统

把 CLD 的干态、推力、PIV 和虚拟质量试验做成可复现实验平台

15 分钟

不同实验使用 ClearPath、ATI Mini-40、NI DAQ、Simulink Real-Time、CPS 和 Photron/DaVis。如何统一配置、时钟、运行状态和数据产物，使每个结果可追溯？

展开实验编排与数据谱系

统一 run manifest

run_id、UTC/monotonic start、operator、specimen/configuration、CLD coverage、材料批次、频率、振幅、U、St、采样率、设备 serial、calibration version、软件 commit 和环境条件。

实验状态机

CONFIGURED → ZEROING → ARMED → WARMUP → RECORDING → COOLDOWN → VALIDATING → COMPLETE/FAILED；只有 RECORDING 窗口进入正式分析，失败保留原因和部分数据。

时钟与触发

DAQ/控制命令/力数据尽量同一硬件时钟；PIV 用明确触发与 phase index；保存原始时间戳和 trigger log，不在采集时只保存相位平均结果。

数据层

raw immutable、calibrated、cycle/phase averaged、figure-ready 分层；每层记录生成脚本、参数和上游 hash。K*/thrust/efficiency/acceleration 都能回到原始 run。

自动 QA

零点漂移、饱和、周期数、频率误差、缺样、PIV valid vector ratio、稳态窗口和重复间差异；不合格 run 标记 excluded + reason，而不是静默删除。

OPTIONAL 10Flow SensingML 数据系统

设计压力 + 稀疏 PIV 到全流场重建的训练与部署系统

15–20 分钟

系统有 54 组流动/几何工况、80 Hz 压力、PIV ground truth 和双路径 attention 模型。怎样组织数据配对、split、版本、指标和在线推理，避免模型靠泄漏取巧？

展开数据与模型系统

数据契约

以 case/run 为一级实体，保存 geometry、St、spacing、trigger、sensor calibration、pressure window、sparse PIV patch、full-field target、mask、units 和 coordinate transform；配对基于 TTL-relative time。

Split

按 case/geometry 拆 train/val/test，不能随机拆相邻 frame；同一周期或同一试验的高度相关样本不得跨 split。phase 若部署时不可得，不能作为 oracle input。

预处理

normalization 统计只从 train 拟合；每通道零偏/缺失 mask 显式保存；转换版本与原始数据 hash 绑定。数据增强必须保持物理坐标和向量符号一致。

指标

不能只用被自由来流像素主导的全场 MSE；同时报告 vorticity SSIM、gradient、peak vorticity、vortex core detection、按 case 泛化和 uncertainty calibration。

部署

在线输入带 freshness 和 missing mask；超出训练分布或 ensemble uncertainty 过高时输出 invalid/降级，而不是强行给漂亮流场。记录 model/data/config version 支持回放。

OPTIONAL 11通用机器人ROS 2 迁移

如果把现有 MantaBot 架构迁到 ROS 2，你会怎样拆节点和 QoS？

15 分钟

要求保留 200 Hz 执行器路径、Steam Deck 控制、双目视频、记录回放和安全行为。说明哪些部分适合 ROS 2，哪些不应盲目消息化。

展开迁移边界与 QoS

节点建议

teleop_gateway、supervisor/state_machine、motor_driver、sensor drivers、stereo_camera、depth_processor、telemetry/recorder、health_monitor。200 Hz trajectory 与 CAN driver 可同进程/组件甚至保留内部直接接口，避免为了“全 ROS”增加序列化和调度抖动。

接口

连续 sensor/state 用 topics；短配置/zero/status query 用 services；长标定或实验流程用 actions。E-Stop 不能只做可能排队的普通 action，应有独立硬件/driver gate。

QoS

camera/高频 telemetry 采用 best-effort、small depth、keep last；低频配置与状态转换用 reliable；需要晚加入者获知的静态配置可 transient local。deadline/liveliness 用于健康契约，但不替代 actuator watchdog。

执行模型

控制 callback 与图像/日志分 callback group/executor；耗时回调不与控制共享单线程 executor；使用 intra-process/loaned message 时仍检查生命周期和数据所有权。

迁移策略

先包裹现有稳定 driver 和协议，通过桥接保持行为；用记录回放对比旧/新输出；性能验收看 P99 loop jitter、端到端 age 和故障行为，不以“topic 能看到”为完成。
